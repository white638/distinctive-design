# 评审 prompt（每轮原样复用）

整段复制，只替换花括号里的内容。Claude Code 与 Codex 用同一份 prompt；评审在 Codex 里收到的是图片附件时，把"以下截图"理解为这些附件。`{产品一句话}` 在第一轮定下后每轮保持一字不改；它只说明产品是什么、给谁用，**不**写设计意图、配色理由或你希望评审注意什么。

---

## 打分式（默认）

> 你是一位眼光极高、观点鲜明的设计总监。请只查看以下截图，不要读取任何其他文件：{截图路径列表}。{可选：另附参考图 {参考图路径}，它们只是质量基准或情绪板，不是要复制的目标。}
>
> 这是一个{产品一句话}。截图依次是桌面端首屏、桌面端分段长图、移动端首屏、移动端分段长图。
>
> 请严格按下面四步的顺序进行，前一步完成之前不要做后一步的判断。
>
> **第一步 描述**：只说画面上有什么，用中性词，不评价。版面分成哪几块，各有什么文字、图像、色块、线条；用了哪些字体气质、颜色、形状。
>
> **第二步 分析**：说这些元素之间的关系。
> - 第一眼：首屏一眼看过去复杂还是简单？能否认出这是哪一类网站或产品？
> - 视觉重量与平衡：视线第一落点在哪？重量偏向哪边？
> - 层级、节奏与疏密：间距是处处相同，还是有疏有密？留白有没有方向？
> - 统一与变化：字号、颜色、圆角、间距的种类是太多、太少还是合适？
> - 巧合：有没有差几像素就对齐、相切、擦边的地方？逐一指出。
> - 细节：字距、对齐、边缘处理、图像质量；有中文时也看中文排版与中西文混排。
>
> **第三步 解读**：根据前两步的事实，说这个设计传达出什么情绪和气质，像什么、让人想到什么。再指出哪些元素看了两遍还不明白它在做什么、为什么在这里。
>
> **第四步 判断**：
> 1. 判断这个设计想要达成的美学方向，想象一家顶级设计工作室会如何执行这一美学。
> 2. 列出当前设计与那个水准之间最大的差距，按影响排序，最多 6 条。每条要具体、可执行（指出哪个元素、改成什么），不要空泛的散文。
> 3. 对显得用烂了、过度堆砌、或一眼就是 AI 生成的模式要明确指出并扣分。这包括"为了显得独特而用的套路"本身。
> 4. 大胆、有主见，不要选安全或容易的建议。
> 5. 最后给出 0–10 分，表示当前设计离那个工作室水准有多近。最后一行格式：`SCORE: X/10`。

## 排名式（有合适参考图时优先）

> 你是一位眼光极高、观点鲜明的设计总监。以下 {N} 组截图分别来自 {N} 个不同的网站，请只查看这些截图，不要读取任何其他文件：
> - A：{路径}
> - B：{路径}
> - ……
>
> 1. 按精致度与品味从高到低排名，每个给一句理由。
> 2. 对排在最后的两个，各列出最多 4 条具体、可执行的差距。
> 3. 最后一行格式：`RANK: B > D > A > E > C`。

参考图与我们的截图打乱顺序、用中性字母编号，不要让评审知道哪个是"我们的"。我们的设计排进前二即视为达标。

## 读评审结果时：对照情绪

评审第三步读出的情绪，是在不知道设计意图的情况下得出的。拿它和 `.design/direction.md` 里写的"想要的感觉"对照：

- 对得上：意图传达到了，按第四步的差距继续改。
- 对不上：这是本轮最重要的差距，排在评审列出的所有差距之前。先找出是哪些元素把感觉带偏了，再处理其他意见。
- 第三步列出的"看了两遍还不明白"的元素：补上它和题材的关系线索，或者删掉。

不要把这个对照结果或设计意图告诉评审，下一轮评审仍然只看截图。

## 如何调用评审

先把填好的 prompt 存成 `.design/critic_prompt.md`，每轮只改其中的截图路径，方便确认每轮 prompt 一致。

**Claude Code**：Agent 工具开一个子代理，prompt 就是上面填好的全文，截图写绝对路径。

**Codex，首选 `design_critic` 子代理**：本 skill 的 `codex/design_critic.toml` 装进 `~/.codex/agents/` 后，Codex 里会多出一个只看截图、不读其他文件、不改文件的评审子代理。明确要求"spawn 一个 design_critic 子代理"，把填好的 prompt 交给它，等它返回。这个文件只是一层约束外壳，评审内容全部来自父代理交给它的 prompt，所以 skill 更新时一般不需要重新安装它。

**Codex，备选：独立的 `codex exec` 进程**（没装 `design_critic`、或子代理不可用时）：

```bash
codex exec --ephemeral -s read-only --skip-git-repo-check \
  -i .design/shots/roundN_desktop_fold.png,.design/shots/roundN_mobile_fold.png \
  --output-schema <skill 目录>/assets/critic-schema.json \
  -o .design/critic_roundN.json - < .design/critic_prompt.md
```

- `--ephemeral` 不留会话记录，`-o` 把最终回复写进文件，`--output-schema` 强制输出与四步对应的 JSON（`description`、`analysis`、`interpretation`、`unclear_elements`、`aesthetic`、`gaps`、`ai_tells`、`score`），分数直接从 JSON 读，不用再从正文里找 `SCORE:` 那一行。用 schema 时，第四步第 5 条的"最后一行格式"可以忽略。
- 排名式不用 schema，直接读回复里的 `RANK:` 行。
- 分段长图较多时，挑首屏加最能代表各区块的 3–4 张，每轮挑法保持一致。

两个宿主都开不出全新上下文的评审时，**不要**自己给自己打分冒充评审：在 `review_log.md` 写"跳过：原因"，改为请用户看截图，或交付时说明未经独立评审。

## 评审记录

每轮在项目里追加 `.design/review_log.md`：

```
## Round N
- 分数 / 排名：
- 评审前三条：
- 本轮实际改了什么：
- 快照：.design/snapshots/roundN/
```

改之前先把当前源码复制到 `.design/snapshots/roundN/`。下一轮分数比上一轮低，就回滚到上一轮快照，换一条评审意见来改。
